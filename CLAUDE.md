## Environment & Tooling Rules

- **OS:** Windows. The Bash tool runs on a POSIX compatibility layer (Git
  Bash/MSYS2), not a real Unix filesystem.
- **NEVER run `find /`, `find ~`, `grep -r /`, or any unbounded recursive search
  from a root-ish path.** MSYS2's `find`/`grep` will walk the entire `C:` drive
  through the Windows filesystem shim, which is extremely slow and can hang the
  session for hours.
- Scope every search: to the project directory (use the `Glob`/`Grep` tools, which
  are fast and sandboxed), or to a specific cache directory when hunting for a
  dependency jar, e.g. `find ~/.gradle/caches -type f -iname 'some-lib*.jar'`.
- If a broad filesystem search is genuinely required (e.g. "where on this machine
  is X installed"), use the `PowerShell` tool with `Get-ChildItem -Recurse` scoped
  to a specific drive/folder — never an unscoped Bash `find`.

## What This Project Is

A **self-hosted, Kotlin-everywhere** rebuild of HomeFlow: a period tracking
application containing highly sensitive menstrual health data. You self-host the
server on a Raspberry Pi (or any homelab box) and access your data from a
**desktop app** and an **Android app** that share most of their code.

The whole stack is Kotlin:

- **Server:** Ktor (JVM), Exposed over PostgreSQL, Flyway migrations.
- **Clients:** Compose Multiplatform + Material 3 — one codebase for desktop
  (JVM) and Android.
- **Shared:** a `:core` KMP module of DTOs + domain math + validation, compiled
  into both server and clients. See `__docs/SHARED-MODULE.md`.
- **Unchanged infra (language-agnostic):** PostgreSQL, **Keycloak** (OIDC + the
  TOTP 2FA), and **Caddy** (TLS reverse proxy).

### Gradle modules (as generated by the KMP wizard)

| Module | Path | Role | Package root |
|---|---|---|---|
| `:core` | `core/` | pure shared: DTOs, domain math, validation, `ApiError` (no Compose/OS/DB) | `org.homeflow.core` |
| `:server` | `server/` | Ktor backend; `api(projects.core)` | `org.homeflow` |
| `:app:shared` | `app/shared/` | shared Compose UI + repo + auth; `androidMain`/`jvmMain` actuals | `org.homeflow.app.shared` |
| `:app:androidApp` | `app/androidApp/` | Android entry point | `org.homeflow` |
| `:app:desktopApp` | `app/desktopApp/` | desktop entry + packaging | `org.homeflow` |

Desktop = the `jvm()` target → **`jvmMain`** source set. The server depends on
`:core` only — **never** on `:app:shared` or Compose.

**The primary user is a single person. There is exactly one user account.** The
data sensitivity means security is a first-class concern, not an afterthought.

> This is a ground-up reimplementation of the original Node/SvelteKit HomeFlow.
> The original's spec docs (data model, API, Keycloak, threat model) are
> authoritative requirements and have been copied here verbatim; its
> implementation docs have been ported to the Kotlin stack (server/client
> architecture, testing, phases, Docker, deployment, branching). Nothing in this
> repo is web-specific anymore.

## Non-Negotiable Decisions

These are fixed. Do not deviate without explicit instruction from the user.

### Architecture
- **Shared-first.** DTOs, cycle/analytics math, validation, and error codes live
  in `:core` and are written **once**. Never duplicate a DTO or domain rule
  between server and client. See `__docs/SHARED-MODULE.md`.
- **Server layering:** Route → Service → Repository → Exposed (DB). Never skip a
  layer. No SQL in route handlers. No business logic in repositories.
- **DB query layer:** Exposed only — no raw JDBC string-building, no ORM-style lazy
  graphs. (SQLDelight was considered and rejected for the server; see
  `ARCHITECTURE-server.md`.)
- **Migrations:** Flyway. Migration files live under `server/src/main/resources/db/migration/`.
  Migrations are **manual**, never automatic on startup.
- **Clients:** Compose Multiplatform + Material 3. Platform differences are
  `expect`/`actual` in `:app:shared` (`androidMain`/`jvmMain`), never `if (isAndroid)`
  branching in shared code.

### Security
- **Row scoping:** every repository function that reads or writes health data
  includes `userId` from the validated JWT (`req`-equivalent principal) — **never
  from the request body**. This is a server-side invariant; clients cannot enforce it.
- **Encryption:** AES-256-GCM at the application layer for `daily_logs.notes` and
  `daily_log_sex.encrypted_payload`. Encrypt/decrypt happens in **server service
  functions only** — never in repositories, route handlers, the `:core` module,
  or any client. Clients exchange plaintext over TLS and never hold the key.
- **`daily_log_sex` is structurally different** from other symptom tables: a
  single `encrypted_payload TEXT` column (encrypted JSON array of option IDs), not
  per-row FKs. See `data-model-sex-encryption-addendum.md`.
- **Client token storage:** refresh token only in platform secure storage
  (Android Keystore-backed encrypted prefs; desktop OS keychain). **Access token
  in memory only.** Never in plaintext files, logs, or shared prefs.
- **No plaintext health data at rest on clients.** In server-connected (remote-only)
  mode, reads/writes go to the server and clients hold in-memory caches only. In
  local-only and offline modes, health data is persisted on-device in a SQLDelight
  store with whole-DB SQLCipher encryption (key derived from the user's passphrase).
  Health data is never written to plaintext files, logs, or unencrypted prefs.
- **`FLAG_SECURE`** on Android; best-effort screenshot/recents protection on desktop.

### Auth
- **Keycloak stays.** Two confidential/public client split as today: a public
  client per app (`homeflow-android`, plus a new `homeflow-desktop`) and the
  confidential `homeflow-backend` for the Ktor server's JWT validation + Admin API.
- **PKCE (S256) is required** on the Authorization Code flow for both clients.
- **JWT validation checks:** `iss`, `aud` (must contain `homeflow-backend`),
  `exp`, `alg` (RS256 only). All must pass or return `401`.
- **The audience mapper must be configured in Keycloak** before JWT validation
  works — the single most common setup mistake. See `KEYCLOAK.md`.
- **2FA is password + TOTP** (authenticator-app code), handled inside the OIDC
  browser/Custom Tab flow by Keycloak. Desktop uses a loopback redirect; Android a
  custom scheme. (WebAuthn passkeys were the original second factor but were dropped:
  a passkey's RP-ID must be a public domain, and Android's Credential Manager will not
  surface any passkey provider for a private LAN hostname like `homeflow.lan`. TOTP has
  no domain binding and works on every platform. See `KEYCLOAK.md`.)

### Testing
- **kotlin.test / JUnit5** for unit tests; **Compose UI tests** for client
  screens (`commonTest`).
- **Integration tests use a real PostgreSQL** via **Testcontainers** — do not
  mock the DB layer.
- **Cross-user access must return `RESOURCE_NOT_FOUND`, not `FORBIDDEN`** — this
  is a security test (don't reveal that another user's resource exists).

## Error Response Shape

All API errors use this exact shape. The Ktor status-pages/error handler enforces
it — handlers throw typed errors, they do not format responses manually. The
shape and codes are defined once in `:core` (`ApiError.kt`).

```json
{ "error": { "code": "RESOURCE_NOT_FOUND", "message": "Daily log not found for the given date." } }
```

| Code | HTTP Status |
|---|---|
| `UNAUTHORIZED` | 401 |
| `FORBIDDEN` | 403 |
| `RESOURCE_NOT_FOUND` | 404 |
| `VALIDATION_ERROR` | 400 |
| `CONFLICT` | 409 |
| `INTERNAL_ERROR` | 500 |

## What Never Gets Logged

These must never appear in any log output, on server or client:

- Request or response bodies
- Health data of any kind
- `user_id` values in plaintext in production
- Tokens, secrets, or credentials

Safe to log: HTTP method, route path, status code, response time, error codes.

> The original Android client took care that the generated OkHttp client's
> BODY-level logging interceptor was **not** used. Preserve that posture: no
> body-level HTTP logging on any client, ever.

## Common Gotchas (carried from the web app — still apply)

- **JWT validation 401s after a successful-looking login** → the Keycloak
  audience mapper is missing/misconfigured; the `aud` claim must contain
  `homeflow-backend`. See `KEYCLOAK.md`.
- **`iss` claim mismatch** → Keycloak's stamped issuer must match what the server
  expects; the canonical hostname (Tailscale `*.ts.net`) must line up across
  `APP_HOSTNAME` and `PUBLIC_KEYCLOAK_URL`.
- **TOTP code rejected** → server/device clock skew (TOTP is time-based; check NTP),
  or the authenticator was enrolled against a since-recreated realm (`down -v`) →
  delete the stale OTP credential in Keycloak and re-enroll on next login.
- **Re-login required every launch** → no `offline_access` granted, or offline
  session idle disabled in the realm.
